Admin and public test ladder — how it works

This page explains the Windows command that runs four Node scripts in order against a local Next.js app. The browser steps use Playwright (playwright ^1.57.0) and launch a real Chromium process. They sign in through the Clerk form, open pages, click buttons, and type into fields on the live app for tenant tenant_demo_002. They do not use Cypress, Selenium, Puppeteer, Jest, or mocked API fixtures.

Run-the-command details also live in Full-site E2E TestSprite guide and TestSprite/E2E_FULL_README.md. The folder name TestSprite is the local suite. This ladder does not call the TestSprite cloud or MCP server.

The command and how Windows runs it

One cmd /c process sets three tenant variables and the app URL, then runs four node scripts one after another. In Windows CMD, && runs the next command only if the previous one succeeded. A single & always runs the next command, even when the previous Node process exits with a failure. That is why inventory, comprehensive admin, CRUD, and smoke are separated with &: a failed page in the comprehensive suite does not skip CRUD or the smoke crawl. The variables from set stay in that same CMD process, so every Node script sees them.

Run the ladder

Environment variables set for every script in the chain:

  • TEST_TENANT_ID — tenant the harness must use
  • E2E_TENANT_ID — same tenant, second accepted name
  • E2E_EXPECTED_TENANT — hard check; the resolved tenant must match or the CRUD and smoke scripts exit immediately
  • TEST_BASE_URL — origin of the Next app, for example http://localhost:3001

Libraries and technique

Technique in one sentence: build a route list from the App Router source tree, then drive one signed-in Chromium session through admin pages (assertions, a few typed searches, and create/save/delete clicks) and through every admin and public route in that list.

The four steps

Order of the command
1. Inventory Filesystem walk. Writes route-inventory.json. No Chromium.
2. Comprehensive Chromium visits about 31 fixed admin URLs. Checks selectors, JS errors, and sign-in redirects.
3. CRUD Chromium clicks Create/Add, types an [E2E] name, saves, then tries to delete that row.
4. Smoke Chromium opens every admin and public inventory route, plus admin-home tile clicks.

Steps 2–4 each launch their own Chromium process. They can reuse the saved Clerk storage state in TestSprite/admin-tests/.auth-state.json so they do not type the password on every script when the cookie is still valid.

1. Route inventory (no browser)

generate-route-inventory.js

generate-route-inventory.js reads the repo. It does not open a browser and does not need the dev server. Later smoke uses the file it writes. The comprehensive and CRUD scripts have their own page lists and do not read this file.

  • Recurses src/app and collects every page.tsx.
  • Drops route groups such as (auth) from the URL.
  • Marks dynamic segments ([id], [...slug], [[...sign-in]]).
  • Classifies each path: admin if it starts with /admin, otherwise public (plus mosc, gas-station, and profile-site when those prefixes exist).
  • Writes TestSprite/generated/route-inventory.json.

2. Comprehensive admin pages

comprehensive-admin-test-suite.js

comprehensive-admin-test-suite.js is a fixed catalog of about 31 admin pages (adminTestPages in that file). Playwright opens each URL with ?tenant= appended. This is a page-render and UI-presence suite. It is not a full create/update/delete pass; that is step 3.

What Chromium does on each page

  1. Launch Chromium (headless from auth.json, default true).
  2. Reuse .auth-state.json if a visit to /admin stays off /sign-in. Otherwise fill the Clerk sign-in form and save the new storage state.
  3. page.goto the admin URL (waitUntil: domcontentloaded), then wait for h1 (or h2 / main) so client components can hydrate.
  4. Fail on a redirect to /sign-in, a visible 404, or a visible unauthorized/forbidden alert.
  5. Fail on critical page errors and console messages (ReferenceError, TypeError, uncaught). A known missing logo 404 is ignored.
  6. Count the CSS selectors listed for that page (tables, search inputs, action buttons).
  7. On failure, save a screenshot under TestSprite/admin-tests/screenshots when screenshotOnFailure is true.

Places it types or clicks, beyond navigation

  • Focus groups: types __testsprite_no_results_xyz__ into #focus-groups-search and expects the empty-search message, then clears the field.
  • Membership plans: extra checks on the plans list UI.
  • Executive committee: types a no-match search, and opens/closes the add-member flow when the controls are present.

The HTML report for this step only is TestSprite/admin-tests/admin-test-report.html. It does not write the coverage files under TestSprite/reports.

3. CRUD on the demo tenant

admin-crud-demo-tenant-suite.js

admin-crud-demo-tenant-suite.js is the step that clicks through create, save, and delete. It uses the same Playwright Chromium session and the same Clerk storage state. Before the browser work, Node calls discoverDemoIds() so ticket types and discount codes can target a real event id from /api/proxy/event-details.

Safe data pattern

Values typed into the live forms:

  • E2E_NAME — [E2E] Demo plus the current timestamp (E2E_PREFIX is [E2E])
  • E2E_CODE — E2E plus the last 6 digits of that timestamp (plan codes are lowercased)
  • Organization domain e2e-<stamp>.example.test and contact email e2e.<stamp>@example.test

For each module the script:

  1. Opens the list URL with ?tenant= and runs smokeCheckPage (main/heading/nav or enough body text, and no visible auth error).
  2. If the module is read-only, it records a pass and moves on. Read-only modules: manage usage, tenant settings, and test Stripe.
  3. Otherwise it opens a known create route (for example /admin/events/new) or clicks the first visible Create/Add control.
  4. Fills the first visible name/title/code field with the [E2E] value, fills extra fields, and clicks Save/Create.
  5. Returns to the list, finds text [E2E], clicks Delete on that row or card, and confirms the dialog when one appears.
A module is marked pass when the list loaded and a name field was filled. The log line still says whether save and delete happened (filled, saved, deleted or filled, not-saved, not-deleted). A missing create button becomes skip when the list itself loaded. A broken list or a thrown navigation error is fail. Rows are real database rows until delete succeeds. Search the tenant for names starting with [E2E] if a run stops mid-module.

4. Inventory smoke crawl

run-inventory-smoke-crawl.js

run-inventory-smoke-crawl.js with --kind=admin,public loads the inventory from step 1 and visits those routes in one Chromium page. Because admin is included, the crawl signs in first. Public routes in this combined run are opened in that same signed-in context.

Admin home buttons (real clicks)

Before the route loop, the script opens /admin?tenant= once per destination in ADMIN_HOME_BUTTONS (Manage Users, Manage Events, Polls, and the other tiles listed in e2e-harness.js). If the tile link is visible, Playwright clicks it and waits for the path to change. If the click does not land, it falls back to page.goto. The report records via: click or via: goto.

Every other route

  • Static paths are opened as-is. Admin paths get ?tenant=.
  • Dynamic paths such as /events/[id] are rewritten with ids from discoverDemoIds(). Event paths use the event id, polls use the poll id, sponsors use the sponsor id, membership subscribe uses the plan id, focus groups use the slug. If a required id is missing, the route is skip, not fail.
  • Optional catch-all segments ([[...sign-in]]) are dropped so the smoke hits the page root.
  • /auth/signout-redirect is skipped on purpose (it would sign the session out).
  • HTTP 500 fails the route. A public URL that still redirects to sign-in is recorded as pass with message auth-gated.
  • smokeCheckPage requires visible structure (main, heading, nav, a container, or more than 40 characters of body text) and rejects a visible auth error.
The smoke crawl does not click every button on every page. Aside from the admin-home tiles, it checks that each route renders. Create/save/delete clicks are the CRUD suite.

How login works

Clerk form, then saved cookies
  1. Credentials come from TestSprite/admin-tests/auth.json (copy auth.json.example). Fields: email, password, baseUrl, tenantId, timeout, headless, screenshotOnFailure.
  2. authenticate-playwright.js goes to /sign-in and tries several selectors (input[name="identifier"], email inputs, then password inputs) because the Clerk DOM can vary.
  3. It presses Enter, and if the page is still on sign-in it clicks a visible Sign in / Continue button.
  4. It polls the URL for up to about 30 seconds. An OAuth redirect (Google and similar) fails the run; the account needs email and password.
  5. Cookies and local storage are written with Playwright storageState to .auth-state.json. The next script loads that file and only retypes the password if /admin bounces back to sign-in.
If every admin URL lands on sign-in, the usual cause is role data: user_profile.user_role for this Clerk user and tenant_demo_002 must be ADMIN or SUPER_ADMIN. The suite does not grant that role itself.

How test data is created

Live app, not a fixture database
NeedHow it is satisfied
Which pages exist Generated from source files. No scenario file of fake routes.
Event, plan, poll, sponsor, focus-group ids First row returned by the running app’s /api/proxy/... lists (size=5, sort=id,desc). These are existing tenant records.
New entities Only the CRUD step creates them, by typing into the real admin forms and clicking Save. Names are prefixed [E2E] so they can be found and deleted in the same run.
Search “no results” checks The comprehensive suite types a nonsense string into a search box. It does not insert a matching database row.
Tenant scope Query string ?tenant=tenant_demo_002 plus the admin tenant field when the URL does not already carry it. Proxy calls from the app still rely on the app’s own JWT and tenant header. The tests do not add tenantId.equals themselves.
Nothing in this ladder stubs fetch, intercepts Stripe webhooks, or resets the database before the run. What you see in the admin UI during a headed run is what the test sees.

Watching the real browser

Headless by default

"headless": true in auth.json still launches Chromium. The window is hidden, which is faster. Set "headless": false to see sign-in, page loads, search typing, Create clicks, and admin-home tile clicks. Comprehensive, CRUD, and smoke all read that flag (config.headless !== false).
