Bedrock LLM — Admin Help Chat and Retail Ask Integration

Shared guide for adwiise-agent-admin and application-deployments. Keep this HTML and the Cursor rule bedrock_llm_admin_help_and_chat_integration.mdc in sync in both repositories.

Use one Bedrock model family (Claude Sonnet on account 224674645062) for two separate product surfaces: Admin Help (how-to for admin pages) and Retail Ask (grounded Q&A on a morning brief). Same model ID is fine; never share the same API route, system prompt, or grounding context.

1. Two chat surfaces

Surface Runs in Grounding Call path
Admin Help adwiise-agent-admin
POST /api/admin/help-chat		 Curated knowledge pack + current pathname Floating Help on /admin/** → Next.js server → Bedrock direct
Retail Ask adwiise-agent-ai-engine
POST /v1/chat		 Saved brief JSON (metrics, cards, forecast) Retail UI → Spring /api/retail-brief/chat → engine ALB → Bedrock
Do not send Admin Help questions to the AI engine /v1/chat or Spring /api/retail-brief/chat. Amplify cannot reach the internal engine ALB; retail Ask must keep that Spring forwarder. Admin Help must not reuse it.

2. Admin Help architecture

Request flow
AdminHelpChat (floating UI on /admin)
  → POST /api/admin/help-chat   (Clerk session + ADMIN / SUPER_ADMIN)
  → retrieveAdminHelpKnowledge(question, pathname, isPlatformSuperAdmin)
  → Bedrock InvokeModel  (or knowledge-pack stub if disabled / invoke fails)
  • Library: src/lib/adminHelp/ (knowledge, retrieve, prompt, bedrock client)
  • API: src/app/api/admin/help-chat/route.ts
  • UI: src/components/admin/AdminHelpChat.tsx mounted from admin tenant layout client
  • Smoke: npm run test:admin-help
Answer rules
  • Answer only from retrieved chunks + page context; never invent menus or routes.
  • Plain English how-to; read-only (no admin mutations).
  • Hide platformOnly knowledge from non–SUPER_ADMIN.
  • Do not fine-tune the model on admin pages — update the knowledge pack instead.

3. Environment variables

BEDROCK_ENABLED=true
BEDROCK_REGION=us-east-1
BEDROCK_MODEL_ID=us.anthropic.claude-sonnet-5-5
Admin Help defaults on unless BEDROCK_ENABLED=false. Amplify Hosting apps are in us-east-2; Bedrock Runtime stays us-east-1. amplify.yml must include BEDROCK_ in the build-time env grep so SSR Lambdas receive the vars.

set-amplify-bedrock-env.ps1 refuses to update if get-app JSON cannot be parsed (SSL warning noise) or the app has fewer than 10 existing env keys. That prevents wiping a full Amplify env down to only Bedrock keys.

6. Bolting Admin Help onto another admin / satellite frontend

  1. Copy src/lib/adminHelp/, the help-chat API route, and AdminHelpChat; mount it in the admin layout client.
  2. Add dependency @aws-sdk/client-bedrock-runtime and the three BEDROCK_* env vars.
  3. Keep Clerk + admin role checks on the API route.
  4. Extend the knowledge pack (hubGuides, howTos, operatorGuides, routeMap) for that product’s tiles — do not dump every HTML PRD into the prompt.
  5. Merge Amplify env (us-east-2 app id) and attach bedrock:InvokeModel to that app’s SSR role.
  6. If the clone has retail, keep Retail Ask on Spring → engine; do not merge the two chat APIs.

8. Anti-patterns

AvoidDo instead
Admin Help → AI engine /v1/chat Next.js /api/admin/help-chat → Bedrock
Browser calling Bedrock with embedded keys Server route + IAM / default credential chain
update-app with only Bedrock keys after a bad JSON parse Merge script with parse + min-key safeguards
Fine-tuning / embedding all admin pages into the model Curated knowledge pack + pathname retrieval
Teaching SUPER_ADMIN-only flows to tenant ADMIN Filter platformOnly chunks
