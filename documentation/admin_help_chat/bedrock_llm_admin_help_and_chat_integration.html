Bedrock LLM — Admin Help Chat and Retail Ask Integration

Shared guide for adwiise-agent-admin and application-deployments. Keep this HTML and the Cursor rule bedrock_llm_admin_help_and_chat_integration.mdc in sync in both repositories.

Use one Bedrock model family (Claude Sonnet on account 224674645062) for two separate product surfaces: Admin Help (how-to for admin pages) and Retail Ask (grounded Q&A on a morning brief). Same model ID is fine; never share the same API route, system prompt, or grounding context.

1. Two chat surfaces

Surface Runs in Grounding Call path
Admin Help adwiise-agent-admin
POST /api/admin/help-chat		 Curated knowledge pack + current pathname Floating Help on /admin/** → Next.js server → Bedrock direct
Retail Ask adwiise-agent-ai-engine
POST /v1/chat		 Saved brief JSON (metrics, cards, forecast) Retail UI → Spring /api/retail-brief/chat → engine ALB → Bedrock
Do not send Admin Help questions to the AI engine /v1/chat or Spring /api/retail-brief/chat. Amplify cannot reach the internal engine ALB; retail Ask must keep that Spring forwarder. Admin Help must not reuse it.

2. Admin Help architecture

Request flow
AdminHelpChat (floating UI on /admin)
  → POST /api/admin/help-chat   (Clerk session + ADMIN / SUPER_ADMIN)
  → retrieveAdminHelpKnowledge(question, pathname, isPlatformSuperAdmin)
  → Bedrock InvokeModel  (or knowledge-pack stub if disabled / invoke fails)
  • Library: src/lib/adminHelp/ (knowledge, retrieve, prompt, bedrock client)
  • API: src/app/api/admin/help-chat/route.ts
  • UI: src/components/admin/AdminHelpChat.tsx mounted from admin tenant layout client
  • Smoke: npm run test:admin-help
Answer rules
  • Answer only from retrieved chunks + page context; never invent menus or routes.
  • Plain English how-to; read-only (no admin mutations).
  • Hide platformOnly knowledge from non–SUPER_ADMIN.
  • Do not fine-tune the model on admin pages — update the knowledge pack instead.

6. Short stub on the hubs, long answer locally

Localhost Admin Help can write a multi-step how-to while https://www.adwiiseagent.ai/admin and https://dev.adwiiseagent.ai/admin return one sentence, for example “Admin Home: Returns to this dashboard so you can open another admin area. It does not edit tenant data.”

That sentence is stubAdminHelpAnswer in src/lib/adminHelp/bedrock.ts. answerAdminHelpQuestion uses the stub when Bedrock is off or when invokeAdminHelpBedrock throws. BEDROCK_ENABLED=true only means the route will try the call. It does not prove the live server has credentials.
Cause confirmed 2026-11-06
  • Both hubs already had BEDROCK_ENABLED=true, BEDROCK_REGION=us-east-1, and BEDROCK_MODEL_ID=us.anthropic.claude-sonnet-5-5.
  • Inline policy AdminHelpBedrockInvoke was on AmplifySSRLoggingRole-1cc46167-ac65-414a-b580-7103432bd70a.
  • computeRoleArn was null, so the Next.js server never assumed that role. The SDK had no credentials and the catch block returned the knowledge-pack stub.
  • Localhost works because the developer credential chain can call Bedrock.

Fix both hubs. Prod app d3gov7yn1ctow1, dev app d3qk5eouzr7b80. The role trust policy must allow amplify.amazonaws.com to sts:AssumeRole.

  1. Read the compute role: aws amplify get-app --app-id <id> --region us-east-2 --query app.computeRoleArn. Add --no-verify-ssl when the CLI fails with CERTIFICATE_VERIFY_FAILED.
  2. Put bedrock-invoke-policy.json on that role as inline policy AdminHelpBedrockInvoke. The us. inference profile needs invoke permission on foundation models and inference profiles in us-east-1, us-east-2, and us-west-2. A us-east-1-only resource list denies the cross-region profile.
  3. Set computeRoleArn with update-app --compute-role-arn only. Do not pass --environment-variables unless the JSON is the full map; that flag replaces every key. Confirm the env key count did not drop.
  4. RELEASE release/v1.0.0. A compute-role change is not live until the next release. Prod auto-build can be off, so start a RELEASE job.
  5. Sign in, ask Help, and inspect POST /api/admin/help-chat. "backend":"bedrock" is the live model. "backend":"stub" means invoke still failed. Read CloudWatch /aws/amplify/<appId> for [adminHelp] Bedrock invoke failed.

7. Bolting Admin Help onto another admin / satellite frontend

  1. Copy src/lib/adminHelp/, the help-chat API route, and AdminHelpChat; mount it in the admin layout client.
  2. Add dependency @aws-sdk/client-bedrock-runtime and the three BEDROCK_* env vars.
  3. Keep Clerk + admin role checks on the API route.
  4. Extend the knowledge pack (hubGuides, howTos, operatorGuides, routeMap) for that product’s tiles — do not dump every HTML PRD into the prompt.
  5. Merge Amplify env (us-east-2 app id), attach AdminHelpBedrockInvoke, and set computeRoleArn to that role. A policy on the service role alone does not reach the Next.js server. Then RELEASE the branch.
  6. If the clone has retail, keep Retail Ask on Spring → engine; do not merge the two chat APIs.

9. Anti-patterns

AvoidDo instead
Admin Help → AI engine /v1/chat Next.js /api/admin/help-chat → Bedrock
Browser calling Bedrock with embedded keys Server route + IAM / default credential chain
update-app with only Bedrock keys after a bad JSON parse Merge script with parse + min-key safeguards
Fine-tuning / embedding all admin pages into the model Curated knowledge pack + pathname retrieval
Teaching SUPER_ADMIN-only flows to tenant ADMIN Filter platformOnly chunks
Treat BEDROCK_ENABLED=true as proof the live chat calls Bedrock Check POST /api/admin/help-chat for "backend":"bedrock"
Leave computeRoleArn null after attaching the invoke policy to the service role Set the compute role, then RELEASE release/v1.0.0
Limit the invoke policy to us-east-1 when the model id starts with us. Allow foundation models and inference profiles in us-east-1, us-east-2, and us-west-2
