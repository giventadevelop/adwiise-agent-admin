Vector database and RAG analysis

Admin Help, image scanning, and retail Ask already share one Bedrock model, us.anthropic.claude-sonnet-5-5 in us-east-1. They do not share context. Only Admin Help retrieves documents before the call. It sends the full help guide for the page the admin is on, plus the best keyword matches from the rest of the knowledge pack.

Updated 2026-11-26. The first version sent only short tile summaries, and real questions got wrong answers. Every admin page now has a full guide generated from its code. The decision to stay without a vector database still holds.

A managed vector database stays out of this design. It would add a monthly floor without making the same model more accurate on the questions these three callers already answer.

Decision
Keep the three call paths. Admin Help sends the current page's full guide plus keyword matches. Image scanning stays a direct model call from Java. Retail Ask stays a direct model call with the one saved brief. The model id stays the same.

Fine-tuning the same model on new pages is the expensive, stale option, because every page change would need another training job. The update path is to change the page and run npm run help:guides. That rewrites only the guides whose page code changed.

A vector database is still not needed. The wrong answers came from missing content and a code bug, not from how chunks were searched.

What went wrong and what changed (2026-11-26)

On Tenant Settings, “how do I update the logo here?” was answered with the default hero images note. That answer came from three separate problems:

The knowledge pack had one-line tile summaries. Nothing described the logo upload, social links, or most other fields on each page. Even a working model could only say “I don't know”. The only chunk containing the word “logo” was the hero images note, so it ranked first. A full guide for each of 57 admin page groups (518 sections), generated from the page code: labels, buttons, help text, file limits, and messages. The whole guide for the current page goes to the model. Tenant Settings has a hand-reviewed guide.
Newer Claude replies can start with a thinking block. The route read only content[0].text. Good model answers were thrown away and replaced by the backup answer. This failed 6 of 40 questions in a live run. Read every text block in the reply.
The backup answer pasted the first 480 characters of the top chunk, whatever the question. Off-topic answers that looked real. The backup now says AI help is unavailable. It quotes saved help only when the title or keywords match the question; otherwise it lists the page's sections. The chat shows a status line under every answer: green “AI answer” or amber “Saved help” with the reason.

The coverage script still passed while all of this was wrong, because it only checks that every tile has a summary. Accuracy is now measured with 40 real questions in scripts/admin-help-eval.json: 40/40 offline and 40/40 with live Bedrock answers.

What each project sends the model

The three projects share the model family. Each caller builds its own prompt. Admin Help does not go through the Java service. The Java Bedrock setting is only image-text-model-id. Retail Ask does go through the Java service, and Spring only forwards to the engine. The engine is what calls Bedrock.

Keep the prompts separate. A shared vector index across help text, images, and retail briefs would mix how-to steps with store numbers and OCR words. Separate prompts are the multi-use design: one model, three contexts.
Where retrieval already works

Admin Help retrieves first, then generates. Most questions are about the page the admin is on. Choosing that page's guide by URL path is exact, and no similarity search can do better. The guide fits in the prompt with room to spare.

A vector index would only help a question asked from a different page in words that no section uses, for example “tuition bill” when the guide says “fee invoice”. The generated guides already list everyday synonyms as keywords. When a real question still misses, add it to the eval set and fix the guide or its keywords.

Caller What a vector store would change
Admin Help Little. The current page's guide covers most questions, and synonym misses are fixed in the guide keywords. Revisit only if the eval set shows cross-page misses that keywords cannot fix. If that happens, use embeddings in a JSON file or pgvector, not a hosted store.
Image scanning There is no document to search. The model has to see the image. RAG does not apply.
Retail Ask The right brief is already in the prompt. A store of past briefs would add questions across many days or stores, such as which shop was short on milk last month. It would not improve today’s single-brief answer.
Cost of adding a vector store

Help traffic is small. A few thousand input tokens and a few hundred output tokens per question, at Sonnet-class Bedrock rates, is on the order of cents per question and tens of dollars a month even at a few thousand questions. Embeddings of the current pack would be a one-time fraction of a dollar. Sending the full page guide adds a few thousand input tokens per question, which is still cents. Generating all 57 guides with npm run help:guides is a one-time cost of a few dollars, and later runs only rewrite guides whose page code changed.

The cost that matters is the store.

Option Monthly floor Use here
Bedrock Knowledge Bases on OpenSearch Serverless On the order of a few hundred dollars even when idle. Larger than the help-chat model bill. Leave it out.
Pinecone or another hosted vector index A similar idle floor. Leave it out.
pgvector on the Postgres already in use, or a JSON file of embeddings next to the chunks No new monthly floor. The only shape that stays cheap, and only if a later product need appears.
Do not add a managed vector database for this change.
How new pages stay current

After changing an admin page, run npm run help:guides to refresh its guide. It needs AWS credentials that can call Bedrock and rewrites only the guides whose page code changed. Review the guide diff in the pull request. Generated guides live in src/lib/adminHelp/knowledge/generated/pageGuides.generated.json; do not edit that file by hand. Hand-reviewed guides go in MANUAL_PAGE_GUIDES in pageGuides.ts.

  • npm run test:admin-help runs the smoke checks, the 40-question eval, and the stale-guide check. It needs no AWS access.
  • npm run test:admin-help:live asks Bedrock the same 40 questions.
  • npm run help:guides:check exits with code 1 when a page changed and its guide was not regenerated.

When an Admin Home tile is added, also add its hub summary and route-map entry, then run check-admin-help-coverage.mjs. That script compares tile keys in src/app/admin/page.tsx with hub guides and route-map feature keys, prints every tile label, path, and summary, and exits with code 0 when every tile is covered. It checks that every tile has a summary. It does not check answer accuracy; the eval set does that.

Parameters: this script reads the repository. It has no command-line flags.

  • src/lib/adminHelp/knowledge/hubGuides.ts — one summary per Admin Home tile
  • src/lib/adminHelp/knowledge/routeMap.ts — path, tasks, and suggested questions
  • src/lib/adminHelp/knowledge/howTos.ts — step-by-step answers, including school fees and staff contacts
  • src/lib/adminHelp/knowledge/pageGuides.ts and generated/pageGuides.generated.json — full page guides

The only later retrieval case

Revisit retrieval only if product wants questions over many days of retail briefs. If that happens, embed brief summaries into the existing Postgres database. Stand up no new vector service, and keep retail numbers out of the Admin Help prompt.

Today’s design: the current page's full guide plus keyword chunks for Help, pixels for image scan, one brief for retail Ask. Same model. Three contexts.
