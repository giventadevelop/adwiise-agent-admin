Vector database and RAG analysis

Admin Help, image scanning, and retail Ask already share one Bedrock model, us.anthropic.claude-sonnet-5-5 in us-east-1. They do not share context. Only Admin Help retrieves documents before the call, and that retrieval is a keyword score over TypeScript files in this repository.

A managed vector database stays out of this design. It would add a monthly floor without making the same model more accurate on the questions these three callers already answer.

Decision
Keep the three call paths. Admin Help keeps stamped chunks. Image scanning stays a direct model call from Java. Retail Ask stays a direct model call with the one saved brief. The model id stays the same.

Fine-tuning the same model on new pages is the expensive, stale option. A page change would require another training job. The help prompt already answers only from the chunks that were retrieved. Adding a hub guide is the update path.

Related guide: Admin Help knowledge coverage.

What each project sends the model

The three projects share the model family. Each caller builds its own prompt. Admin Help does not go through the Java service. The Java Bedrock setting is only image-text-model-id. Retail Ask does go through the Java service, and Spring only forwards to the engine. The engine is what calls Bedrock.

Project Call What is in the prompt Retrieval
adwiise-agent-admin Admin Help Next.js server InvokeModel in src/lib/adminHelp/bedrock.ts System rules plus up to 8 stamped chunks from src/lib/adminHelp/retrieve.ts Keyword score over TypeScript in src/lib/adminHelp/knowledge/. This is already retrieve-then-answer. It is not a vector index.

The three call paths
Admin Help chat → Next.js help-chat → keyword chunks → Bedrock Claude Retail Ask → Spring RetailEngineClient → AI engine POST /v1/chat → Bedrock Claude Image scan → Java BedrockImageTextService → Bedrock Claude
Keep the prompts separate. A shared vector index across help text, images, and retail briefs would mix how-to steps with store numbers and OCR words. Separate prompts are the multi-use design: one model, three contexts.
Where retrieval already works

Admin Help is already retrieve-then-generate. The pack is about 55 tiles plus short how-tos. Eight chunks fit in the prompt. A vector database does not make that more correct for questions whose words match the guides.

A vector index would help only when someone asks with different words than the keywords, for example “tuition bill” when the chunk says “fee invoice”. That miss is fixed by adding those words to the chunk. The school how-to already does this.

Caller What a vector store would change
Admin Help The current keyword pack already answers matching questions. Synonym misses are fixed in the knowledge files.
Image scanning There is no document to search. The model has to see the image. RAG does not apply.
Retail Ask The right brief is already in the prompt. A store of past briefs would add questions across many days or stores, such as which shop was short on milk last month. It would not improve today’s single-brief answer.
Cost of adding a vector store

Help traffic is small. A few thousand input tokens and a few hundred output tokens per question, at Sonnet-class Bedrock rates, is on the order of cents per question and tens of dollars a month even at a few thousand questions. Embeddings of the current pack would be a one-time fraction of a dollar.

The cost that matters is the store.

Option Monthly floor Use here
Bedrock Knowledge Bases on OpenSearch Serverless On the order of a few hundred dollars even when idle. Larger than the help-chat model bill. Leave it out.
Pinecone or another hosted vector index A similar idle floor. Leave it out.
pgvector on the Postgres already in use, or a JSON file of embeddings next to the chunks No new monthly floor. The only shape that stays cheap, and only if a later product need appears.
Do not add a managed vector database for this change.
How new pages stay current

Update 2026-11-26: short tile summaries were not enough. A question such as “how do I update the logo here?” on Tenant Settings had nothing to match. Every admin page group now has a full page guide generated from its code, and the whole guide for the current page goes to the model. Still no vector database. After changing a page, run npm run help:guides, then npm run test:admin-help. Details: Admin Help knowledge coverage.

When an Admin Home tile is added, update the knowledge files and run check-admin-help-coverage.mjs. That script compares tile keys in src/app/admin/page.tsx with hub guides and route-map feature keys. It prints every tile label, path, and summary. Exit code 0 means every tile is covered.

Parameters: this script reads the repository. It has no command-line flags.

  • src/lib/adminHelp/knowledge/hubGuides.ts — one summary per Admin Home tile
  • src/lib/adminHelp/knowledge/routeMap.ts — path, tasks, and suggested questions
  • src/lib/adminHelp/knowledge/howTos.ts — step-by-step answers, including school fees and staff contacts

The only later retrieval case

Revisit retrieval only if product wants questions over many days of retail briefs. If that happens, embed brief summaries into the existing Postgres database. Stand up no new vector service, and keep retail numbers out of the Admin Help prompt.

Today’s design: keyword chunks plus the current page’s full guide for Help, pixels for image scan, one brief for retail Ask. Same model. Three contexts.
