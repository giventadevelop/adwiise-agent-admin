3. Get webhooks into the local app

A payment in Stripe Checkout does not change the billing card by itself. Stripe sends an event to the app's webhook at /api/webhooks/stripe, and the webhook sets the card to Active and adds a row to the Charges table. On a local machine Stripe cannot reach localhost, so something on the machine has to fetch the events and hand them to the app. There are two ways.

Option A: stripe listen (the normal way)

Restart the listener before every test session. Do this every time, and always after the machine has slept or hibernated. A listener window left open across sleep or hibernate can error out or stop delivering events. Go to its terminal, press Ctrl+C, and run the command again. A freshly started listener works fine.

Run this in its own terminal, in a normal Command Prompt or PowerShell window, and leave it open for the whole test.

Setup: Stripe listener
🔧 Customize Parameters:
stripe listen --forward-to http://localhost:3001/api/webhooks/stripe --all-snapshot
Windows Single-Line:
stripe listen --forward-to http://localhost:3001/api/webhooks/stripe --all-snapshot
  1. Wait for the line Ready! Your webhook signing secret is whsec_....
  2. That value must equal STRIPE_WEBHOOK_SECRET in .env.local. If it differs, paste the new value into .env.local and restart the admin app.
  3. Each payment then prints lines such as checkout.session.completed followed by [200].
If the listener shows an error or the card stays on Payment due, first stop it with Ctrl+C and start it again. Use Option B only if a fresh start still fails. More detail is in section 6.

Option B: the stand-in script

Use forward-stripe-events.cjs when a freshly restarted stripe listen still cannot connect, or to catch up on events that fired while the listener was off. It does not stay running. Run it once after each payment, from the root of the admin project.

Forward recent Stripe events
🔧 Customize Parameters:
node scripts/platform-billing/forward-stripe-events.cjs --minutes=15 --port=3001
Windows Single-Line:
node scripts/platform-billing/forward-stripe-events.cjs --minutes=15 --port=3001
⚙️ Script Parameters
ParameterDefaultMeaning
--minutes15How far back to look for events. Raise it to catch up after the app was down, for example 1440 for one day.
--port3001Port the admin app listens on.
🔍 What the Script Does
  1. Reads STRIPE_SECRET_KEY and STRIPE_WEBHOOK_SECRET from .env.local. It stops if the key is not a test key.
  2. Asks Stripe for events from the last N minutes. It takes only the six event types platform billing acts on: checkout.session.completed, checkout.session.async_payment_succeeded, checkout.session.async_payment_failed, invoice.paid, invoice.payment_failed and customer.subscription.deleted.
  3. Signs each event with the webhook secret and posts it to http://localhost:3001/api/webhooks/stripe, oldest first.
  4. Remembers the ids it delivered in a file in the system temp folder, adwiise-platform-billing-forwarded-events.json. A second run does not send the same event again.
Limits. One run reads at most 100 events. It does not need STRIPE_WEBHOOK_SECRET to match a listener, because it signs with whatever value the app already has.
📊 Example Script Output
invoice.paid in_1Ue4LIK5BrggeAHMM5R3mgOo billingId=- product=- -> 200 {"ok":true,"billingScope":"platform_tenant"}
checkout.session.completed cs_test_a0bSuq... billingId=3 product=EVENT_SITE -> 200 {"ok":true,"billingScope":"platform_tenant"}
Forwarded 2 event(s) from the last 15 minute(s).

A 200 with "billingScope":"platform_tenant" means the app accepted the event. A 400 that mentions the signature means .env.local was changed and the admin app was not restarted.

6. When stripe listen stops working

🔄 Restart it after sleep or hibernate

stripe listen works on this machine when it is started fresh in a normal terminal window. This was confirmed on 20 November 2026: a listener started at 10:14 PM with the command in section 3 ran without error.

  • The listener holds a live connection to Stripe. Sleep and hibernate break that connection. A listener window that was open before the machine slept may show an error, or sit there and deliver nothing.
  • The fix is to restart it. Press Ctrl+C in the listener window and run the command again.
  • Make the restart a habit: restart the listener before every test session, even if the window looks healthy.
After a restart, check three things. The window prints Ready! Your webhook signing secret is whsec_.... That value equals STRIPE_WEBHOOK_SECRET in .env.local. After the next payment the window prints event lines ending in [200].
Events that fired while the listener was off are not sent later. After restarting, run forward-stripe-events.cjs once with --minutes covering the gap. See section 7.
⚙️ The certificate error seen during the automated test

During the automated test the Stripe CLI was run from the assistant's own command shell, not from a normal terminal window. There it stopped with this message every time, including at a moment when the listener in the normal terminal was running:

Post "https://api.stripe.com/v1/stripecli/sessions": tls: failed to verify certificate: x509: certificate signed by unknown authority (possibly because of "crypto/rsa: verification error" while trying to verify candidate authority certificate "Norton Web/Mail Shield Root")
  • The message names Norton's Web/Mail Shield. In that shell, the CLI was handed a certificate signed by Norton in place of Stripe's, and refused it.
  • Why that shell is treated differently from a normal terminal was not investigated.
  • This is the reason forward-stripe-events.cjs was written. It runs on Node, which reached Stripe from that shell without trouble.
If you ever see this certificate error in your own terminal, restart the listener first. If a fresh start still shows it, use forward-stripe-events.cjs for that session. Changing the antivirus settings is your decision and was not done during this test.

7. Does the webhook retry when the app is down?

🔁 It depends on how the event is delivered
SetupApp or listener was downHow to catch up
Local machine with stripe listen No automatic retry. The listener forwards an event once, at the moment it happens. An event that happens while the listener is closed, stalled after sleep or hibernate, or while the app is stopped, is not sent later. Run forward-stripe-events.cjs with a larger --minutes. Or resend one event with stripe events resend evt_... while the listener is running.
Local machine with the stand-in script Nothing is lost. The script pulls events from Stripe when you run it. Run it again with --minutes covering the gap. An event that got a failed response is tried again on the next run.
Staging or production with a webhook endpoint registered in the Stripe Dashboard Stripe retries by itself. In live mode it keeps trying with growing gaps for up to three days. In a sandbox it tries a few times over a few hours. Usually nothing. For a longer outage, resend the failed events from the Stripe Dashboard under Developers, Webhooks, the endpoint, its event deliveries.
Stripe keeps events for 30 days. Anything older cannot be listed or resent. The retry periods above are Stripe's documented behaviour and were not measured in this test.
Sending an event twice is safe here. The webhook sets the same status again, and the charge ledger skips an event whose Stripe event id it already stored, so no second Charges row appears.
📊 How to tell that a webhook was missed
  • Stripe returned you to ?checkout=success, but the card still reads Payment due.
  • The payment is in the Stripe dashboard, but the Charges table has no row for it.
  • list-platform-subscriptions.cjs shows an active subscription for a billing row whose card is not Active.

In each case, run the forward script for the period in question and reload the page.

9. One subscription per billing row: today and the plan

The rule to aim for is simple: one billing row has at most one live Stripe subscription. A price change updates that subscription. It does not cancel it and create another. Updating in place is the standard Stripe practice, because it keeps the saved card, the invoice history and the billing date. Cancel and create is only needed when the customer or the currency changes.

⚙️ The fault found in this retest: the wrong organization

The Stripe page showed a different email on each visit: contact1@example.com, then gain@hotmail.com, and others. Seven checkouts used seven different organizations.

  • Cause. Checkout looked up the tenant's organization with /api/tenant-organizations?tenantId.equals=.... The backend has no tenant filter on that list, so it returned the first organization it had. Each checkout saved a new Stripe customer id on that organization, which moved a different organization to the front for the next call.
  • Effect. The paid subscription in step B, sub_1Ue6Z3K5BrggeAHM39cdEZys, was created on the customer of the organization Giventa Inc. The website kcnj_parsippany_8 belongs to the organization KCNJ Temp, id 15, whose Stripe customer is cus_VfFYZA9U5jYLVf. Step C then failed because the app looked for the subscription on the right customer and did not find it.
  • Fix. loadOrganization in stripeCheckout.ts now reads the tenant's settings, takes the linked organization id, and loads that organization. Pay monthly also counts the subscription the row already holds, even when it sits on another customer.
  • Cleanup done. sub_1Ue6Z3K5BrggeAHM39cdEZys was canceled in the sandbox.
