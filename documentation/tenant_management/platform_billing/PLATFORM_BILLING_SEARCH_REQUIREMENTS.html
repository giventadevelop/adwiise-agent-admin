Platform Billing: Search and Billing History Requirement

This page answers one question: does the platform billing area need a search over charges and billing history, so a super admin can answer a customer, check a payment, or refund it? Yes. It was written on 21 November 2026 after reading the admin project adwiise-agent-admin, the backend adwiise-agent-service, and the schema file adwiise_agent_Latest_Schema.sql. Phase 1 was built the same day. Section 9 lists what was built and where it differs from this requirement. Phase 2 is not built.

The work is split in two. Phase 1 is search and history, and needs no table change. Phase 2 is refunds, and needs a schema change and three decisions from you.

3. Phase 1: search and history

Result table. When, Organization, Website, Fee, Plan, Amount, Status, Period, Invoice. Organization and Website link to their billing pages. Newest first. When and Amount can be sorted.

Paging. 20 rows a page, paged by the backend, with the same pager the other billing tables use.

Totals. One line above the table: the number of charges found and the dollar sum for each status.

Export. Exports every row that matches the filters, not the page on screen, up to 5,000 rows. Over that, the page asks for a narrower search.

Tiles. Each status tile on the platform billing home opens this page with that status chosen.

One row per invoice. A bank debit writes an Open row and later a Paid row. The table shows the newest row of each invoice, as the website page already does, and the detail panel shows both.

3.2 Charge detail

Clicking a row opens a panel with everything the ledger holds for it.

  • Organization, website, fee, plan, billing scope, amount, currency, interval.
  • Period start and end, the time of the charge, the failure reason, the notes.
  • Invoice, subscription, payment and event ids, each with a copy button and a link that opens it in the Stripe dashboard. The link goes to the sandbox dashboard when the key is a test key.
  • The other ledger rows of the same invoice, oldest first.
  • The five newest change history rows of the same website and fee.
  • In Phase 2, the Refund button and the refund history.
3.3 Change history

A second tab on the search page, and a section on each website and organization billing page. It reads platform_billing_assignment_event.

  • Filters: organization, website, fee, date range. The backend supports all four today.
  • Columns: When, Organization, Website, Fee, Old plan, New plan, Old amount, New amount, Changed by, Reason.
  • Changed by shows the name and email of the user, looked up from the stored user id.
3.4 The Charges table on the website pages

This is the table on /admin/platform-billing/[tenantId] and on /admin/billing.

  • Add a Fee column: Event site, Retail locations, or Organization fee.
  • Add a Period column.
  • Add three filters above the table: Fee, Status, and a date range.
  • Page through the whole history from the backend, instead of the 50 newest rows.
  • The super admin gets a link “Open in charge search” that carries the website over as a filter.

4. Phase 2: refunds and disputes

💵 Refund a charge from the detail panel
  • Who: the platform super admin only.
  • Which charges: a Paid charge with a payment id. The button is hidden on any other row.
  • Form: the amount, filled with what is still refundable, and a reason, which is required. A second click confirms, and the text states the amount, the organization, and that Stripe cannot undo a refund.
  • What it does: asks Stripe for the refund. The ledger is not written by the button. It is written when Stripe sends charge.refunded, so a refund made in the Stripe dashboard is recorded the same way.
  • Ledger: a full refund sets the status Refunded. A part refund keeps the row Paid and shows the refunded amount beside it.
  • The subscription is not canceled by a refund. The panel says so and links to the website page, where Cancel now is.
  • Paid period: a full refund ends the paid period of that charge, so the grace and lock rules apply again.
  • History: every refund is written to the change history with the user and the reason.
The ledger table has no column for a refunded amount, a refund id or a Stripe charge id, and its status list has no value for a dispute. Phase 2 needs these added to platform_billing_charge: refunded_amount_usd, stripe_refund_id, stripe_charge_id, and the status DISPUTED in the check constraint. Follow .cursor/rules/database_schema_guidelines.mdc for the change.

Disputes. When a customer disputes a charge with their bank, Stripe sends charge.dispute.created and later charge.dispute.closed. The webhook marks the row Disputed, and the search can filter on it. Answering the dispute stays in the Stripe dashboard.

8. Decisions needed

❓ Before Phase 2 is built
  1. Refund in this app, or in the Stripe dashboard only? Recommended: build the webhook part first, so a refund made in Stripe shows as Refunded here. Add the button after that. The webhook part is needed either way.
  2. Part refunds? Recommended: yes. A customer who removes a location in the middle of a month is the common case for Retail.
  3. Should a tenant admin see the change history of their own website? Recommended: yes, without the name of the platform user who made the change.
  4. Does a full refund lock the website again? Recommended: it ends the paid period, and the normal grace days then apply. It does not lock at once.
Phase 1 needed no decision and is built. See section 9.

↔️ Where the build differs from sections 3 and 5
  • Organization and Website are not type-ahead lists. The Find box takes the organization name, number, email or part of a website id. The Website id box takes the exact id.
  • The tables show every ledger row. An Open or Failed row whose invoice was paid afterward carries the words “Paid later”. Showing one row per invoice does not work when the backend pages the list.
  • The Plan filter uses the plan id. The ledger stores the id of the plan and leaves plan_code empty.
  • Sorting is a list named Order, not a click on the column heading.
  • Change history is a tab on the search page. The website billing page links to it with the website chosen. The organization billing page has no link yet.
  • A website id typed into Find finds the organization that owns the website, and so shows the charges of all its websites. Use the Website id box for one website.
