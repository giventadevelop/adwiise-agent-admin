Squad roster tables and tenant settings

Read from adwiise-agent-database-repo/SQLS/Current_Sqls/adwiise_agent_Latest_Schema.sql on 31 October 2026. The seven tables in the screenshot are one roster. They are not copies of tenant settings.

A tenant is one organization, stored on tenant_organization. That organization has one settings row, tenant_settings, and any number of squads. The settings row decides whether the public homepage shows the squad. The seven roster tables hold the squads, the people, the sports they play, and the awards. None of those seven tables has a foreign key to tenant_settings.

Where a new website fits

A group that wants its own website chooses a site type. A discussion group, a political interest group, and a social club use EVENT_ORG. That site type already turns on events, gallery, news, and membership. It does not turn on tournaments. Adding a new site-type code would not open any extra screen, because an unknown module key already uses the events preset.

Team type is a second label, used only when that same site wants named groups on the roster. team_groups.team_type stores a text code from the team_type catalog. Shared codes include SPORTS, MUSIC, OTHER, DISCUSSION, SOCIAL, POLITICAL, CULTURAL, VOLUNTEER, YOUTH, and COMMITTEE. The member form shows jersey and season totals only for SPORTS, and instruments only for MUSIC. Every other code keeps name, biography, photo, and the sports checkboxes.

How a tenant owns these tables

Every roster row that belongs to one club carries that club’s tenant_id. The id points at tenant_organization.tenant_id. Deleting the organization deletes the settings row and the roster rows, because those foreign keys use ON DELETE CASCADE.

tenant_settings is a sibling of the roster, not its parent. The settings table also points at the same organization, and tenant_id is unique there, so each tenant has exactly one settings row. The only settings column that talks about this roster is show_team_members_section_in_home_page. When that flag is true, the homepage shows the squad section. The flag does not contain players, sports, or groups.

Two catalog tables in the screenshot, sports_category and team_type, are allowed to have an empty tenant_id. An empty tenant id means the row is a shared platform choice, such as Cricket or Sports. A filled tenant id means that one organization added a private choice of its own. Operational tables (team_groups, team_members, and the three link tables) always require a tenant id.

What each table is, in plain English

sports_category

The menu of sports. Seeded rows with an empty tenant id are Cricket, Football (Soccer), Basketball, Volleyball, Tennis and Squash, Badminton, Table Tennis, and Golf. Any tenant can use those. A tenant that needs a sport that is not on the list adds its own row with its tenant id. The code must be unique among shared rows, and unique again inside one tenant.

team_type

The menu of roster kinds. The shared rows are Sports, Music, and Other. This answers “is this group a squad or a band?” It does not list the sports inside the squad. A music band and a football squad can live in the same tenant.

team_groups

One named group on the public carousel: First Team, Choir, and so on. It must have a tenant id. team_type on this table is the catalog code copied into a text column (SPORTS, MUSIC, OTHER). There is no foreign key to team_type.id. The slug is unique per tenant when it is filled in.

team_members

One person in one home group. team_group_id is required, so a person cannot be saved with no home squad. The row also holds identity (name, photo, email), football season totals (appearances, goals, assists, wins, draws, losses), and two JSON-like text fields: recent_matches for football match rows, and sport_profiles for every other sport’s stats and matches. An optional user_profile_id can point at a login, and that link is cleared if the login is deleted. The person row itself is removed if the home group or the organization is deleted.

team_member_sport

The checked sports for one person. One row is one person plus one sports_category. The pair cannot be inserted twice. The schema comment says this table replaced the old categories list inside sport_profiles. The JSON column is still there for the extra numbers (points, wickets, match box scores). You cannot delete a sport from the catalog while a person still points at it (ON DELETE RESTRICT).

team_group_membership

Extra squads for a person who already has a home squad. The schema comment says a person can belong to more than one squad in the same tenant, and that team_members.team_group_id stays the primary group. Each membership can store its own jersey number and position. The pair of group and person is unique.

team_member_achievement

One award, honor, trophy, or cap for one person. category is a required text code such as AWARD. achievement_category_id is an optional pointer at the achievement_category catalog, which is the same shape as sports_category but was not in the screenshot. The award disappears with the person.

How the rows connect
From To What it means
tenant_settings.tenant_id tenant_organization.tenant_id One settings row per organization. Unique.
team_groups.tenant_id tenant_organization.tenant_id The squad belongs to that club. Not to the settings row.
team_groups.team_type team_type.code Text match only. No foreign key. A renamed catalog code will not update old groups.
team_members.team_group_id team_groups.id Home squad. Required. Deleting the squad deletes its people.
team_members.tenant_id tenant_organization.tenant_id Copied onto the person as well as the group. Nothing in the database checks that the person’s tenant matches the home group’s tenant.
team_member_sport team_members and sports_category Which catalog sports this person plays.
team_group_membership team_groups and team_members Additional squads. Unique per group and person.
team_member_achievement team_members and, optionally, achievement_category Awards. The category code is stored even when the catalog id is empty.
tenant_settings.show_team_members_section_in_home_page the roster, by convention Homepage visibility only. No foreign key.
Where the same fact is stored twice

The seven tables should stay. They answer different questions. The overlap is inside a few columns, not a second copy of a whole table.

What is repeated Where What to treat as the source
Which sports a person plays team_member_sport and the categories array inside team_members.sport_profiles The link table. The service rewrites the JSON list from the checked sports after save. The rest of the JSON (stats and matches) is not a copy of another table.
Which squad a person belongs to team_members.team_group_id and a row in team_group_membership The column on the person is the home squad and is required. The membership table is for extra squads. If the home squad is also inserted as a membership, jersey and position can drift between the two rows.
Jersey and position team_members and team_group_membership Useful when the same person wears a different shirt in a second squad. Redundant only when both rows describe the same squad.
Football season totals versus other sports Real columns on team_members (goals, assists, recent_matches) and the same ideas inside sport_profiles for basketball, cricket, and the other codes Football stays on the columns. Other sports stay in the JSON. Do not copy football into sport_profiles. The shapes match on purpose so editors can use one card layout.
Award category team_member_achievement.category (required text) and achievement_category_id (optional foreign key) This is the clearest duplication. The text can disagree with the catalog row. The catalog id is the safer pointer. The text remains because older rows and the form still send a code.
Group kind team_type catalog and team_groups.team_type text The catalog is the list of allowed labels. The group stores a copy of the code. There is no foreign key, so the database will not stop a group from keeping a code that was later turned off.
Tenant id on every child Person, award, sport link, and membership all store tenant_id even though the home group already has it Kept so lists can filter by tenant without joining. It is a copy of the organization id, not a second organization. A bad write could put a person in one tenant and a home group in another. The schema does not forbid that.

sport_profiles is still the right place for per-sport stats. Replacing it with another table would repeat a wide set of nullable numbers for every sport, or turn into a pile of name/value rows. The redundant part is only the categories list inside that JSON, because team_member_sport already stores those choices.

What looks alike and is not a duplicate
  • sports_category and team_type share the same column layout (code, label, sort order, active flag, optional tenant id). They are two lists. Merging them would mix “Basketball” with “Music”.
  • team_type code SPORTS is not the site type SPORTS_TEAM on site_type_catalog. Site type says what kind of website the organization is. Team type says what kind of group sits on that website. A church site can still have a sports squad.
  • tenant_settings.show_profile_achievements_section is the personal-profile timeline. It is not team_member_achievement. The names are close. The tables are not.
  • Leagues and tournaments are other tenant-owned tables. Homepage and header flags on tenant_settings show them. They do not replace team_groups or sports_category.
  • Social links on tenant_settings are the club’s public pages. Social links on team_members are that person’s pages.

Nothing in the screenshot is an unused second copy of tenant_settings. The roster is tenant data. Settings are the switch. Keep both. When editing a person, trust team_member_sport for selected sports, team_members.team_group_id for the home squad, and sport_profiles only for the extra stat document.
